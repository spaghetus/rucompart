# Usage

"rucompart" is a Rust library aiming to accomplish something similar to the "libcompart" C library. It provides macros to make it easier to set up `tarpc` services by forking a single binary or starting them separately and connecting them over TCP or Unix sockets. It also provides simple abstractions for setting up direct message passing between compartments for advanced usage.

## API

(More detailed documentation on signatures can be generated automatically using `cargo doc`)

### The `Compartmentalize` macro

The `compartmentalize` takes the family of types produced by `tarpc` and implements `Compartmentalize`.

Given a service called `FooService` and an implementation called `FooImpl`, it should be invoked like this:

```rust
compartmentalize!(
    "FOO", // Name of the service.
    ServeFooService, // A type generated by `tarpc`
    FooImpl, // Your implementation struct.
    FooServiceClient, // A client stub generated by `tarpc`
    // A function which runs when the compartment starts.
    // A fork service might do something like dropping to an unprivileged user here, or it might be used to initialized some kind of shared state.
	async fn setup(
		service: &mut Self::Server,
		mode: rucompart::CompartmentMode,
	) -> Result<_, std::io::Error> {
		Ok(())
	}
);
```

### The `Compartment` trait

This trait is the main abstraction of `rucompart`, but it shouldn't be implemented manually. It's implemented on your service struct by the `compartmentalize` macro.

The `fork` method is used to fork the program into host and compartment. It is safe to call manually, but can also be called as part of the `compartment_connect` macro.

```rust
// The function's signature:
fn fork(
    // The first argument is a thread-safe thunk to initialize the server.
    server: impl FnOnce() -> Self::Server + Send + Sync
    // The second argument is needed due to limitations of the trait solver; it might be possible to remove in a future Rust version.
    // It can be generated by passing the tarpc client stub type to the `client_thunk` macro.
    // It takes the typed channel and actually creates the client shim.
    client: impl FnOnce(CompartmentTransport<Self, UnixStream>) -> JoinHandle<Self::Client>
)
// This function can only be called outside of a `tokio` runtime, but the work of constructing the client requires one, so that phase is returned as a future.
-> Result<impl Future<Output = Self::Client>, Self::Error>

fn main() -> eyre::Result<()> {
    // Fork, phase 1
    let client = SomeImpl.fork(|| SomeImpl.serve(), client_thunk!(SomeServiceClient))?;
    Runtime::new()?.block_on(async move {
        // Phase 2, now that the tokio runtime exists.
        let client = client.await;
        // Now we have a client for the service.
    });
}
```

The `connect_to_` and `listen_on_` families of methods are used for similar purposes; the `stream` methods are generic over any async-read-writable type, while the `tcp` and `unix` methods wrap it to accept TCP and Unix socket addresses. Additionally, the wrapper methods spawn their own `tokio` runtime for ease-of-use when called near `fork`. Their arguments are analogous to the respective arguments in `fork`, though the methods in the `listen_on_` family take a server directly instead of indirected through a thunk.

### Channels

Channels are used to establish a TCP connection between compartments wherever they may be running, as long as they're allowed to talk to one another on an arbitrary port. This is the signature of the `Channel` struct:

```rust
pub struct Channel<
    C, // Either () or a `tarpc` transport over TCP taking S and receiving R.
    K, // A marker type; `Once` for a single-use channel or `Many` for a reusable one.
    S, // A serializable type which this channel will send.
    R  // A deserializable type which this channel will receive.
>;

// Type-aliases to write the two states of a channel concisely.
pub type PlannedChannel<K, S, R> = Channel<(), K, S, R>;
pub type EstablishedChannel<K, S, R> = Channel<Transport<TcpStream, R, S, Json<R, S>>, K, S, R>;
```

This is how channels are used:

```rust
async fn listener() -> eyre::Result<()> {
    // 1: Start listening and generate the client part.
    // The S and R type parameters can usually be inferred by the compiler, so I don't have to write them here.
    let (ours, theirs) = channel::<Many>(list_of_socket_addresses).await;
    // 2: Send the client part
    send_to_them_somehow(theirs);
    // 3: Wait for the client to connect to us
    let mut ours = ours.await;
    // 6: Send a message
    ours.send(1i32).await?;
    // 9: Receive a message
    let n = ours.recv().await?;
    assert_eq!(n, 2);
}

async fn connector() -> eyre::Result<()> {
    // 4: Receive the client part
    let ours = recv_from_them_somehow();
    // 5: Establish the channel
    let mut ours = ours.connect()?;
    // 7: Receive a message
    let n = ours.recv().await?;
    // 8: Send a response
    ours.send(n+1).await?;
}
```

`Once`-channels behave the same, except their `send` and `recv` methods move the channel (thus destroying it) instead of borrowing.

## Limitations

Because of how `tokio` is designed, it's impossible to "forget" (that is, destroy without running any `Drop`s that would try to clean up shared resources) the runtime after it's started, so it would cause untold chaos if the `fork` compartment entry-point was used at any time except immediately after the program starts.

Also, channels don't perform anything like NAT punchthrough or relaying, and they use an arbitrary open port, so compartments using channels must be permitted to reach each other on all TCP ports.

Channels abuse TCP/IP somewhat - they'll usually pick the best connection available, but this isn't guaranteed; they'll instead pick the *first* one to finish connecting. They'll also start connections to *all* the peer's addresses before checking if any of them are open, which may be undesirable in constrained environments. If multiple connections succeed, the losers are closed, so this still won't result in an excessive number of open file handles.
